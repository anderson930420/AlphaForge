# SignalForge → AlphaForge E2E Workflow

This document explains how SignalForge and AlphaForge connect through a file-based v0.2 package contract.

The important architectural point is separation of responsibility:

```text
SignalForge = data / signal generation layer
AlphaForge  = signal validation / research artifact layer
```

AlphaForge does not import SignalForge runtime code. SignalForge exports files. AlphaForge validates and consumes those files.

## Why this boundary exists

The projects are intentionally decoupled:

- SignalForge can evolve its upstream data-cleaning and signal-generation logic independently.
- AlphaForge can validate any conforming external signal package, not only SignalForge output.
- The interface is auditable because it is a directory of CSV / YAML / JSON artifacts.
- Backtest and research-validation artifacts are generated by AlphaForge, not embedded in SignalForge packages.

This makes the relationship closer to a data contract than a Python package dependency.

## High-level flow

```text
Raw / processed data
  → SignalForge signal generation
  → AlphaForge v0.2 package export
  → AlphaForge package smoke validation
  → AlphaForge custom_signal research validation
  → metrics / equity curve / drawdown / trade log / Streamlit showcase
```

## SignalForge output contract

A SignalForge → AlphaForge v0.2 package is a directory containing:

```text
market_data.csv
signal.csv
signal_contract.yaml
data_quality_report.json
manifest.json
README.md
```

### market_data.csv

Canonical OHLCV data consumed by AlphaForge:

```text
datetime, open, high, low, close, volume, symbol
```

### signal.csv

AlphaForge v0.2 signed signal schema:

```text
datetime, available_at, symbol, asset_id, signal_name, score, direction, target_weight, source
```

Core semantics:

```text
direction =  1  long
             0  neutral / flat
            -1  short

target_weight ∈ [-1.0, 1.0]
```

### signal_contract.yaml

Human-readable signal contract metadata. It should describe schema version, signal semantics, execution assumptions, and expected consumer behavior.

### data_quality_report.json

Machine-readable data-quality output from the upstream SignalForge generation process.

### manifest.json

Machine-readable package manifest used by AlphaForge for compatibility checks.

The manifest should identify the generator, schema version, execution semantics, and package contents. It should not claim AlphaForge backtest metrics or strategy performance. AlphaForge is responsible for producing validation metrics after ingesting the package.

### README.md

Human-readable package notes for the exported package.

## SignalForge side

From SignalForge, the export command should generate the package directory.

Example shape:

```bash
PYTHONPATH=src python3 -m signalforge.cli export-alphaforge-v02-smoke \
  --output-dir artifacts/signalforge/alphaforge_v02_smoke
```

The exact SignalForge command name may evolve, but the output package must satisfy the AlphaForge v0.2 file contract above.

The SignalForge side should stop at package generation. It should not embed AlphaForge validation outputs into `manifest.json`.

## AlphaForge side: package smoke validation

AlphaForge can smoke-test a v0.2 package with:

```bash
PYTHONPATH=src python3 -m alphaforge.cli smoke-signalforge-package \
  --package sample_data/signalforge/demo_v02_package
```

This checks that AlphaForge can consume the package, validate the manifest/schema boundary, load the v0.2 signal, and run a signed long/short smoke backtest.

Use this when you want to prove the file contract works before running a full research-validation protocol.

## AlphaForge side: research validation

After the package smoke passes, run AlphaForge research validation using the package's `market_data.csv` and `signal.csv` as frozen external inputs.

Conceptual command:

```bash
PYTHONPATH=src python3 -m alphaforge.cli research-validate \
  --data artifacts/signalforge/alphaforge_v02_smoke/market_data.csv \
  --symbol <SYMBOL> \
  --strategy custom_signal \
  --signal-file artifacts/signalforge/alphaforge_v02_smoke/signal.csv \
  --signal-name <SIGNAL_NAME> \
  --development-start <YYYY-MM-DD> \
  --development-end <YYYY-MM-DD> \
  --holdout-start <YYYY-MM-DD> \
  --holdout-end <YYYY-MM-DD> \
  --train-size <N> \
  --test-size <N> \
  --step-size <N> \
  --output-dir artifacts/signalforge/alphaforge_validation
```

This stage is AlphaForge's responsibility. It validates schema and signal/market alignment, then runs development/holdout evaluation and walk-forward validation through the existing `custom_signal` path.

## Responsibility split

| Responsibility | SignalForge | AlphaForge |
|---|---:|---:|
| Upstream data preparation | yes | no |
| Signal generation | yes | no |
| Package export | yes | no |
| Package compatibility checks | limited | yes |
| Manifest/schema validation | produces manifest | validates manifest |
| Backtest/research validation | no | yes |
| Metrics/equity/drawdown/trade artifacts | no | yes |
| Streamlit showcase presentation | no | yes |
| Live trading / broker execution | no | no |

## What AlphaForge assumes

AlphaForge assumes the package is already generated and frozen.

For `custom_signal` validation, AlphaForge does not search over SignalForge internals. It treats `signal.csv` as an external signal artifact and validates the result under AlphaForge's backtest and research-validation protocol.

## What AlphaForge does not assume

AlphaForge does not assume:

- SignalForge is installed as a Python package
- SignalForge internals are importable
- SignalForge generated profitable alpha
- SignalForge package metrics are trustworthy without AlphaForge validation
- `available_at` currently drives runtime execution timing
- the current runtime is a multi-symbol portfolio engine

## Current limitation

The current AlphaForge `custom_signal` runtime validation path is single-symbol.

If a SignalForge package contains multiple symbols, AlphaForge can still consume the package, but runtime validation should select one symbol at a time until multi-symbol portfolio validation is implemented.

## Interview explanation

A concise interview-safe explanation:

```text
SignalForge is my upstream signal-generation layer. It exports a standardized v0.2 package containing market data, signal rows, a contract file, a data-quality report, and a manifest. AlphaForge consumes that package without importing SignalForge code. It validates the package contract, treats the signal as frozen external input, and runs the research-validation protocol to produce metrics, equity curves, drawdown, trade logs, and showcase artifacts. This keeps generation and validation responsibilities separate.
```

## Recommended demo sequence

```text
1. Show SignalForge package files.
2. Run or show `smoke-signalforge-package` output.
3. Run or show AlphaForge `research-validate` output for `custom_signal`.
4. Open generated artifacts in the Streamlit showcase.
5. Explain boundaries: no live trading, no alpha claim from fixtures, current one-symbol validation.
```

## Data hygiene

Do not commit private or licensed raw market data to public git.

Preferred real-data workflow:

```text
raw data stays local
→ SignalForge exports a package locally
→ AlphaForge validates locally
→ derived, permission-safe artifacts are packaged for showcase upload
```
